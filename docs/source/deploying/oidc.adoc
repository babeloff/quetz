Use a confidential OIDC client to authenticate browser users and API clients and supply the server roles defined by xref:../qeps/qep-001-user-permissions.adoc[QEP 1].
For a workload with namespace-scoped credentials,
network policy,
and TLS ingress,
see xref:kubernetes.adoc[Deploy Quetz on Kubernetes with Keycloak].
The provider must expose discovery,
JWKS,
and authenticated token introspection endpoints.

== Set up the identity provider

. Create a Keycloak realm and an OpenID Connect client named `quetz`.
Enable client authentication and the standard authorization code flow.
Require PKCE with the `S256` method.
. Register the exact redirect URI `https://packages.example.org/auth/oidc/authorize`.
Replace the hostname with your Quetz deployment's public hostname.
Configure the reverse proxy so Quetz sees the public HTTPS scheme and hostname.
. Create client roles `owner`,
`maintainer`,
and `member`.
Assign roles explicitly to users or groups.
Leave users without a role when they should only read their own user data and public content.
. Ensure access tokens and introspection responses include `resource_access.quetz.roles`,
`preferred_username`,
`iss`,
`sub`,
`aud`,
and `exp`.
Configure an audience mapper that includes `quetz` in access tokens intended for this API.
Do not rely on roles belonging to another client or on the token's authorized-party field as an audience check.
. Copy the client secret into the Quetz service's `QUETZ_OIDC_CLIENT_SECRET` environment variable.
Keep it outside the tracked configuration file.

See the https://www.keycloak.org/docs/latest/server_admin/index.html[Keycloak administration guide] for client roles and audience mappers and the https://www.keycloak.org/securing-apps/oidc-layers[Keycloak OIDC endpoint reference] for introspection.

The example supplements the existing database,
session,
and package storage configuration.
Set a strong persistent session secret and enable `session.https_only` in production.
Restart Quetz and select *Sign in*,
or open `/auth/oidc/login`.
The browser callback validates state,
nonce,
issuer,
audience,
expiry,
and the ID token's asymmetric signature.
The access token must also pass introspection and have the same subject as the ID token.

By default only OIDC authenticators are registered.
Legacy sessions and Quetz API keys are rejected,
and the development dummy-login endpoint is disabled whenever OIDC is configured.
Set `only = false` only during an intentional migration that requires legacy authenticators and keys.
Existing accounts are never linked automatically by matching usernames or email addresses.
Resolve a username collision explicitly before migrating that account.
Existing channels and package memberships stay attached to their existing user IDs.

== Call the API

Obtain a short-lived access token from the provider with audience `quetz`.
Send it in `Authorization: Bearer <access-token>` to the existing API endpoints.
Use a separate confidential client with service accounts enabled for automation,
map only the required Quetz client roles,
and configure the API audience on its tokens.
Do not use ID tokens as API credentials.

Every authenticated API or browser request checks the access token through authenticated introspection and synchronizes the database server role.
Provider outages fail closed with HTTP 503;
invalid or inactive tokens return HTTP 401.
Quetz does not refresh access tokens automatically;
a browser user must sign in again after expiry.
Browser cookies contain an encrypted access token inside the signed session.
Keep access tokens small enough to fit the browser's cookie size limit.
Quetz logout clears the local session;
provider logout and provider session revocation are managed separately in Keycloak.

Keycloak may return the roles carried by an already issued token until that token is refreshed or replaced.
For urgent role revocation,
revoke the relevant provider sessions or tokens and verify that introspection returns `active = false`.
Removing a role in the provider alone does not guarantee immediate invalidation of all previously issued tokens.

== Configuration reference

All scalar options support the corresponding `QUETZ_OIDC_` environment variable.
Configure the `roles_claim` list in TOML.

[cols="1,1,3",options="header"]
|===
|Option |Default |Meaning
|`issuer` |Required |Exact trusted issuer URL;
discovery is loaded from its `/.well-known/openid-configuration` path.
|`client_id` |Required |Confidential client used for login and introspection.
|`client_secret` |Required |Secret for the confidential client;
prefer `QUETZ_OIDC_CLIENT_SECRET`.
|`audience` |Client ID |Required access-token audience.
|`roles_claim` |`["resource_access", "{client_id}", "roles"]` |Nested path to a list of role names;
`{client_id}` is replaced with the configured client ID.
Use `["realm_access", "roles"]` only if realm-wide roles are intentionally authoritative.
|`owner_role` |`owner` |Provider role mapped to server owner.
|`maintainer_role` |`maintainer` |Provider role mapped to server maintainer.
|`member_role` |`member` |Provider role mapped to server member.
|`only` |`true` |Accept only OIDC authentication when configured.
|`allow_insecure_http` |`false` |Allow HTTP issuer and discovery endpoints for isolated local testing only.
|===

Role mappings must be distinct and nonempty.
Missing or unrecognized roles grant no server role.
When several mapped roles are present,
the highest role wins.
The legacy `[users]` role lists,
default role,
and automatic channel creation do not grant privileges to OIDC identities.

== Validation and deployment acceptance

The implementation at https://github.com/babeloff/quetz/commit/b80b63b[b80b63b]
was verified on 2026-11-25 with 949 server tests passing and 23 skipped.
Its 65 OIDC tests use a mocked provider with real asymmetric ID-token signatures.
They cover state,
nonce,
PKCE,
issuer and audience checks,
role hierarchy and removal,
identity collisions,
API permissions,
revocation,
encrypted-session tampering,
and rejection of legacy authentication bypasses.
Legacy OAuth tests exercise the complete login state exchange through in-process HTTP transports.
Ruff,
formatting,
and mypy passed.
A locally built Linux conda package was installed into an isolated Pixi workspace and started with only the OIDC authenticator registered.

These checks do not establish acceptance against a live Keycloak deployment.
Before enabling a production realm,
verify the following with that realm and its configured proxy:

. Complete a browser login using the exact public callback URI and API audience.
. Exercise the null,
member,
maintainer,
and owner roles against ordinary,
private,
and mirrored channels.
. Remove mapped roles,
obtain a replacement token,
and confirm that the server role is removed on the next authenticated request.
For urgent revocation,
confirm that revoked tokens become inactive at introspection and receive HTTP 401 from Quetz.
. Confirm that legacy sessions and Quetz keys fail in OIDC-only mode and that introspection outages return HTTP 503.

Provider configuration,
reverse-proxy behavior,
and provider revocation latency remain deployment-specific acceptance checks.
