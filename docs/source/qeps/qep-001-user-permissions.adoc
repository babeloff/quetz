== Status

Implemented with provider-managed OIDC server roles in 0.11.1.
See xref:../deploying/oidc.adoc[Configure OIDC with Keycloak] for deployment steps and configuration reference.
Legacy authentication remains available when OIDC is not configured.

== Problem

Authentication alone must not authorize a public server's users to create channels,
mirror external repositories,
or administer other users.
Server permissions require explicit grants and a hierarchy that supports ordinary users,
administrators,
and super-administrators.

== Role hierarchy

A user's server role is one of `owner`,
`maintainer`,
`member`,
or database null.
New OIDC identities without a mapped role have a null role.
The hierarchy is `owner > maintainer > member`.

[cols="1,3",options="header"]
|===
|Role |Server permissions
|Null |Read the user's own data;
read public content.
Explicit channel and package memberships still apply.
|`member` |All above;
create ordinary channels.
|`maintainer` |All above;
read all users' data;
create mirror and proxy channels;
access every channel including private channels.
In the legacy local-role mode,
assign or remove member roles for users with no higher role.
|`owner` |All above;
administer all server roles.
|===

Channel and package roles remain separate grants.
A null server role does not revoke explicit channel or package membership.

== OIDC authority

Browser login uses the authorization code flow with PKCE,
state,
nonce,
and signature-validated ID tokens.
Browser sessions and bearer API requests validate access tokens through the trusted issuer's authenticated introspection endpoint.
Only active,
unexpired tokens with the configured issuer,
API audience,
and a nonempty subject are accepted.

OIDC identity is the pair of issuer and subject,
independent of email and display name.
Provisioning never links an existing account by username or email.
The role source is an explicitly configured claim path,
which defaults to Keycloak client roles in `resource_access.<client_id>.roles`.
Only mapped roles grant privileges;
the highest matching role wins.
Every authenticated request synchronizes the server role,
including removal of all mapped roles.
Legacy configuration role lists and default-role settings do not override OIDC roles.

An identity provider may return roles from the issued token until refresh or reauthentication.
Administrators must revoke provider sessions or tokens for immediate invalidation when supported by the provider.
Quetz fails closed when introspection is unavailable.

== Role API

`GET /api/users/{username}/role` returns the stored role subject to the existing user-data permissions.
The value reflects the last successful synchronization for an OIDC user.
An OIDC user can authenticate again to synchronize newer token claims.

`PUT /api/users/{username}/role` returns HTTP 409 for provider-managed identities.
Change those roles in the identity provider.
In the legacy mode,
the endpoint accepts a JSON object with a nullable `role` field.
Owners can assign or remove any server role.
Maintainers can assign or remove `member` only when the target is currently a member or has no server role.
Members and users without a role cannot assign or remove server roles.

== API credentials

With OIDC-only authentication enabled,
use provider-issued access tokens in `Authorization: Bearer <access-token>`.
Use provider service accounts for automation.
Quetz API key creation is disabled,
and existing local keys are rejected in this mode.

Without OIDC,
`POST /api/api-keys` retains the legacy behavior:
an empty `roles` list creates a key with the user's server permissions;
explicit channel or package roles restrict the key to those scopes.
An intentional migration may set `oidc.only = false` to keep legacy keys and authenticators available.

== Storage

The existing nullable `User.role` column stores the effective server role.
The existing identity table stores the OIDC issuer and subject under provider `oidc`.
No database schema migration is required.
